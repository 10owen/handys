# 스테이메이트 (StayMate) — 동행 취향으로 숙소 고르기

핸디즈 과제 제출물. **작업자: Owen.** 운영/예약/숙박 도메인에서 문제 하나를 정의하고, 그 핵심만 돌아가는 작은 결과물로 구현.
이름은 "동행(mate)과 함께 고르는 숙소(stay)".

- 실행: `docker compose up -d --build` 후 http://localhost:8080 (앱) · http://localhost:8080/schema.html (DB 스키마) · http://localhost:8080/api/docs (API)
- 구성: MySQL 8 (스키마·시드 자동 적재) + FastAPI (해석기·파생 테이블·추천) + nginx (정적 앱 + `/api` 프록시). 컨테이너 3개, 테이블 13개.
- 해석기 프로토콜: `docs/INTERPRETER_PROTOCOL.md` — 자유 문장을 읽는 AI 해석기는 이번 범위 밖, 인터페이스만 정의.
- AI 활용 기록: `AI_LOG.md`(작업 단위별 요청·출력·검토·결과) · `CLAUDE.md`(AI 세션 지시문)

---

## 1. 문제 정의

**숙박 예약은 결제하는 사람 한 명이 하지만, 숙소가 마음에 드는지는 동행자가 판단.** 커플·친구·가족 여행이 그 전형.
숙소 비교는 앱 외부에서 일어나므로 여행 인원들은 채팅방에서 서로 링크를 보내 확인해야 하고, 숙소를 포함한 다른 여행 관련
메시지들이 뒤섞여 숙소 고르기가 불편한 경험이 됨.

이 과정을 앱 안으로 들여와 소셜미디어적인 방식으로 풀어내면 일종의 놀이처럼 느껴지고, 동행자 취향이 앱에 쌓여 다음 여행에서
재사용됨. 레지던스형 숙소는 OTA 여러 곳에서 팔리지만 취향 프로필은 자사 앱에만 있으므로 재예약이 앱으로 회귀.
이를 통해 PU Retention 상승을 기대.

따라서 이 기능의 주 대상은 커플·친구·가족 단위의 레저 여행. 1인 여행·출장·장기체류는 예약자가 곧 판단자라 대상 밖.

## 2. 범위 판단

### 넣은 것 (세 층의 취향 데이터, 같은 태그 어휘)

| 층 | 언제 얻는가 | 무엇 | 결과물에서 |
|---|---|---|---|
| 1. 기본 취향 | 공유 링크로 들어와 1회 | 이름 입력 → 사진 선택지 5문항 → 태그 가중치 | 콜드스타트. 본인이 직접 응답. 저장 시 바로 가입, 테스트 때 적은 이름이 닉네임(변경 가능) |
| 2. 여행 컨텍스트 | 여행 방을 만들 때 | 누구와·인원·지역·목적 키워드 (+ 선택: 세부 장소·날짜) | 카탈로그를 걸러 후보 5개를 미리 담아 줌 (탐색 공수 절감). 장소·날짜는 기록만, 아직 필터에 미사용 |
| 3. 선별 행동 | 후보를 고르는 동안 | 유지/탈락 + 이유 태그 + 한 줄 | 탈락 숙소의 특징과 이유에서 "이 여행이 추구하는 키워드"를 학습. 같은 멤버·같은 동행 유형의 다음 여행에 재사용 |

추천 점수 = 멤버들의 기본 취향 + 이전 여행에서 학습한 것 + 이번 여행에서 학습한 것 + 여행 컨텍스트.
후보마다 "맞음/어긋남" 태그와 그 출처(누구의 취향인지, 여행 목적인지, 학습인지)를 표시.

3층이 핵심. 테스트는 "말한 취향"이지만 탈락은 "드러난 취향"이라 신호가 더 강함.
에어비앤비 공동 위시리스트는 비슷한 역할이지만 후보를 같이 보는 데서 끝나고 선호도로 연결되지 않음. 차별점은 거기에 있음.

### 발전 방향 (순서대로)

1. **소셜미디어 연동** — 인스타그램과 같은 플랫폼과 연동해 숙소·여행 사진 업로드를 유도. 앱 홍보와 바이럴 유도.
2. **체크아웃 후 동행자 피드백** — `events.type = checkout_feedback` 저장은 이미 가능. 유지/탈락 학습과 실제 만족의 차이를 재서 가중치 보정.
3. **AI 해석기** — `api/interpreters/ai.py` 의 `interpret` 구현 → `ACTIVE_INTERPRETERS` 에 추가 → `POST /api/admin/reinterpret`. 자유 문장 해석과 어휘 확장의 시작.

### 성공 지표 (검증 방법)

취향 테스트 완료율 · 미리 추천된 후보 중 실제 예약 비율 · 이 기능을 쓴 예약자의 재예약률과 앱 직접예약 비율 (미사용 대조군 대비).

## 3. 설계·구현

### 데이터: 원칙 하나

**키워드가 아니라, 키워드를 만든 원본 행동을 저장.** 해석 방식은 반드시 바뀜. 원본 이벤트가 있으면
해석기를 바꿔도 전체 프로필 재생성 가능, 키워드만 저장하면 그 순간의 해석에 고정. 그래서 테이블은 네 계층 13개.
(`db/init/01_schema.sql`, 실행 중에는 http://localhost:8080/schema.html 에서 컬럼·FK·행 수 확인 가능.)

| 계층 | 테이블 | 성격 |
|---|---|---|
| 사전 | **`tags`**, `stays`, `choices` | 취향 어휘는 고정 목록이 아니라 **자라는 트리**(`parent`·`status`·`source`, 숫자 `id`). 숙소 특징은 `stays.tags` JSON. 선택지는 한 테이블에 가중치 `[{tag_id, score}]` 를 부착 |
| 원본 | `users`, `trips`, `trip_members`, `trip_candidates`, `stay_likes`, `stay_comments`, **`events`** | 사람이 한 일. `events` 는 append-only (quiz_answer / vote / vote_removed / like / unlike / comment / candidate_added / trip_created / trip_decided / trip_deleted / checkout_feedback) |
| 해석 | **`event_interpretations`** | 해석기가 이벤트 하나를 `{tag_deltas, new_tags, rationale}` 로 번역한 결과. `tag_deltas` 는 `[{tag_id, weight, confidence, evidence}]`(`tags.id` 참조). 이벤트 × 해석기마다 한 행 |
| 파생 | **`taste_profiles`** (유저 × base·커플·친구·가족), **`trip_keywords`** (여행 전체·멤버별) | 해석 결과의 합. 언제든 삭제·재생성 가능 |

처음 안은 18개. 선택지 텍스트를 테이블 6개로 나누고 규칙을 별도 테이블로 뒀으나, 리뷰에서 두 가지 지적을 받아 수정.
(1) 고정 태그 목록은 "피드백이 쌓일수록 취향이 분화된다"는 설계와 모순 → 어휘를 트리로, 해석기가 자식 태그를 제안하는 구조로.
(2) 사용자 피드백을 코드 규칙으로 해석하면 예외 처리가 끝이 없음 → 해석을 교체 가능한 부품(해석기)으로 분리, 자유 문장은 AI 해석기 몫으로 프로토콜만 정의.

### 해석기 (`api/interpreters/`, 규약은 `docs/INTERPRETER_PROTOCOL.md`)

- 해석기는 `interpret(event, ctx) → Interpretation` 하나만 구현. DB 접근 없음.
- **rules-v1** (동작): 선택지 코드 → `choices.tag_weights`(`[{tag_id, score}]`, `tags.id` 참조), 유지 → 그 숙소 태그 +1, 탈락 → 이유 선택지의 가중치만.
- **notes-v1** (동작): 표에 남긴 한 줄을 키워드 사전으로 번역. 유지 표의 "바다 보이는 게 좋았어" → 바다뷰 +2·해변 +1, 탈락 표의
  "너무 복잡해" → 도심상권 −2·조용함 +1, "주방이 없어서 아쉬움" 은 아쉬움 표현이라 원하는 것(주방 +2)으로. confidence 0.7. 카드의 표 옆에 해석 결과 표시.
- **ai-claude** (인터페이스만): 자유 문장·탈락 맥락·체크아웃 피드백을 읽고, 기존 어휘로 안 되면 기존 태그의 **자식으로** 새 태그를 제안. `confidence` 임계값 미만은 합산에서 제외. 프롬프트 초안은 `api/interpreters/ai.py`.
- 같은 이벤트에 두 해석이 나란히 남고, `ACTIVE_INTERPRETERS` 가 합산 대상을 결정. AI 를 붙이는 순서: 구현 → 목록에 추가 → `POST /api/admin/reinterpret`. 스키마·프론트는 변경 없음.

### 숙소 데이터 (`scripts/scrape_yanolja.py` → `db/init/03_stays.sql`)

- 출처는 야놀자(NOL) 숙소 상세 페이지. 핸디즈 지점은 어반스테이·르컬렉티브 ID 20개를 웹 검색으로 수집(상세가 아닌 페이지 2개 제외),
  일반 숙소는 야놀자의 공개 목록 페이지("○○ 근처 호텔·리조트 추천 베스트 10", 도시·구 단위 30개)에서 ID 를 모아 도시당 2~8개씩 추가.
  숙소당 1회(1.5~2초 간격) 요청. 목록 페이지 일부는 403 으로 막혀 제주·전남·경북은 적음. robots.txt 가 막는 `/search/` 와 `/reviews/` 는 미사용.
  지역별 수는 `data/stays_scraped.json`.
- 저장 항목: 이름·브랜드·지역·주소·최대 인원·평점·리뷰 수·편의시설·객실 타입·소개 한 줄·원본 URL. **리뷰 원문은 저장하지 않음.**
  페이지에 실린 리뷰 30~60건을 키워드 사전(깨끗·깔끔·청결 → 청결, 역·지하철 → 역세권, 바다·오션 → 바다뷰 …)으로 훑어
  상위 5개 키워드와 빈도만 `stays.review_keywords` 에 저장. 부정 키워드(좁음·냄새·소음)는 극성 부착.
- `stays.tags` 는 편의시설·객실 타입·이름·브랜드·리뷰 키워드(3건 이상)에서 규칙으로 도출. 리뷰에서 나온 새 어휘(청결·조용함·편의점 인접·친절·비대면체크인)는
  `tags` 에 추가 — "어휘가 자란다"는 프로토콜을 숙소 쪽에서 먼저 적용한 셈.
- 한계: 1박 요금은 클라이언트 렌더링이라 HTML 에 없어 `price_tier` 는 브랜드·객실 유형으로 추정. 키워드 사전은 수작업이라
  "전망"처럼 넓게 잡히는 것이 있음. 스크래핑 시점(2026-09-18)의 스냅샷이며 SQL 로 고정해 컨테이너 기동 시 네트워크 불필요.

### 백엔드 (FastAPI, `api/`)

- `scoring.py` — 규칙 로드, 가중치 계산, 파생 테이블 재계산, 추천 점수. `main.py` — 라우트와 데모 시드. ORM 없이 SQL 직접 사용.
- **쓰기 경로**: 취향 테스트·투표·후보 추가는 전부 `events` 에 한 줄 append → 활성 해석기가 돌아 `event_interpretations` 에 저장 →
  그 유저의 `taste_profiles` 와 그 여행의 `trip_keywords` 를 해석 결과의 합으로 재생성.
  표 취소도 삭제가 아니라 `vote_removed` 이벤트. 현재 표 상태는 이벤트를 순서대로 접어서 복원.
- **읽기 경로**: `GET /api/trips/{id}` 가 보드 한 장에 필요한 것을 전부 반환 (컨텍스트 키워드, 학습 키워드, 후보별 점수·근거·표, 더 담을 후보).
- **점수** = Σ멤버 base + Σ멤버 (동행유형 프로필 − 이번 여행 키워드) + Σ멤버 이번 여행 키워드 + 컨텍스트(`choices` companion/purpose) + 좋아요 × 5. 하드 필터 = 지역·인원.
- **학습**(rules-v1) = 유지는 그 숙소의 모든 태그 +1(남긴 숙소의 특징은 드러난 선호) + 이유 선택지 가중치. **탈락은 이유에서 나온 키워드만 −.**
  탈락에는 이유가 있으므로 숙소 특징 전체를 부정 신호로 잡지 않음(처음엔 전체 −1 이었으나 "편의점 인접 −1" 같은 오독을 낳아 제거).
  이유를 안 고르면 탈락은 학습 신호 없음. 화면(취향 패널·여행 키워드·근거 문장)은 |가중치| 2 이상만 표시. 이유는 고정 태그("비싸서" → 가성비 +2) 또는
  "그 숙소의 해당 범주 태그"(`@parent:뷰` — "뷰가 별로" → 그 숙소의 뷰 하위 태그 −2).
- **재활용** = 같은 멤버가 같은 동행 유형으로 새 여행을 만들면 `taste_profiles[동행유형]` 이 초기 정렬에 반영.
- **해석기 교체** = `POST /api/admin/reinterpret` 가 모든 이벤트를 다시 해석하고 파생을 재생성. 원본은 불변.
- **리뷰 창** = `GET /api/events` 가 원본 이벤트와 그 해석(가중치·근거·rationale)을 나란히 표시. `GET /api/tags` 가 어휘 트리(candidate 포함).
- **활용 인터페이스** = `GET /api/users/{id}/profile?context=커플` 이 `{tag: weight}` 를 반환. 추천·마케팅 세그먼트·운영 수요 분석이 이 하나를 사용.

### 프론트 (`app/`)

- 프레임워크·빌드 없는 HTML 한 파일. 서버에 없는 것(지금 보는 사람, 열린 여행)만 브라우저에 보관.
- `schema.html` 은 `information_schema` 를 읽어 테이블을 네 계층으로 표시. 리뷰용이자 "구조가 곧 설명"이라는 의도.
- **초대 흐름**: 헤더의 "설문 링크 공유"가 `index.html?invite` 링크를 복사(보드에서 누르면 `&trip=ID` 가 붙어 테스트 후 그 여행에 합류).
  링크로 들어온 사람은 이름만 적고 테스트 → 저장하는 순간 가입(테스트 버전이라 별도 가입 단계 없음). 닉네임은 테스트 때 이름이
  기본값, 결과 화면과 메인의 "닉네임 바꾸기"로 언제든 변경. 스키마의 `users.nickname` NULL 상태(게스트)는 유지해 두어, 가입을 분리하려면 프론트만 변경하면 됨.
- 숙소 카드에 야놀자 평점·리뷰 수·리뷰 키워드 상위 5개(빈도)와 원본 링크 표시.
- 여행 보드는 지도 중심. 왼쪽 목록(후보 · 더 담을 수 있는 숙소, 적합도순) · 가운데 지도(추천 등급 5단계 — 강력추천·추천·중간·비추천·매우비추천 —
  를 색과 크기로: 강력추천이 크고 진한 빨강, 매우비추천이 작고 옅은 회색. 등급은 그 여행의 최고점 대비 비율. 테두리 진한 핀 = 후보, 반투명 = 탈락) ·
  오른쪽 상세. 목록이나 핀을 누르면 지도가 그 숙소로 이동하고 상세에 "이번 여행에 맞는 이유"·리뷰 키워드·표·유지/탈락/담기 표시.
  아무것도 안 골랐을 때 상세에는 여행 컨텍스트와 학습 키워드 표시. 지도 중심은 세부 장소가 숙소 이름·주소에 있으면 그 숙소, 아니면 지역 중심.
- 여행 이름에 지역·장소 이름(부산, 속초, 강남, 애월 …)이 들어가면 지역과 세부 장소 자동 입력. 직접 바꾼 뒤에는 덮어쓰지 않음.
- 상세에서 **좋아요**(♥)와 **댓글** 가능. 멤버 한 명의 좋아요는 그 여행 점수에 +5 (근거 줄에 "♥ ○○이 좋아요를 눌렀어요 +5"),
  취향 학습에는 유지 표보다 약한 신호(그 숙소 특징 +1)로 반영. 목록에 "○○이 좋아하는 숙소예요!" 표시.
  댓글에 URL 이 있으면 서버가 OpenGraph(제목·설명·이미지)를 읽어 미리보기 카드 부착. 네이버 지도는 장소 정보를 OpenGraph 로 주지 않아
  링크 카드만 표시 — 실서비스라면 네이버 지역검색·카카오 로컬 API(키 필요)로 장소 정보 수신.
- 상세의 **이 숙소로 결정**이 그 여행의 최종 숙소를 기록(`trips.chosen_stay_id`). 이후 같은 멤버가 든 여행에서 그 숙소가 후보에 오르면
  "🏠 오웬·지민이 묵은 곳 · 작년 10월 부산 커플 (2025년 10월)" 을 목록과 상세에 표시.
- 시연용 이력: 멤버 10명(각자 취향 테스트 완료), 결정 숙소가 있는 과거 여행 4개(부산 커플·속초 친구·제주 커플·강릉 가족), 진행 중 여행 1개(강릉 친구 5명)를
  첫 기동 때 이벤트로 생성. 이 이력 덕에 데모 여행의 근거에 "지난 커플 여행에서 좋아한 바다뷰" 같은 줄이 실제로 등장.
- 참여 멤버가 인원보다 적으면 보드 머리에 "N명 중 M명만 참여 중이에요. 링크를 공유해서 친구를 초대해보세요!" 배너와 초대 링크·복사 버튼 표시.
  링크로 들어온 친구는 이름 → 취향 테스트 → 자동 가입 → 그 여행 보드로 바로 진입.
- 취향 테스트 선택지는 사진 카드. 사진은 Wikimedia Commons 의 CC·퍼블릭도메인 이미지 14장(720px), 출처·저작자는 `app/img/CREDITS.md`. 사진 경로는 `choices.image` 컬럼에 있어 선택지와 함께 데이터로 관리.

### 트레이드오프

- 가중치는 손으로 정한 정수. 통계적 학습이 아니라 "이 신호가 이 방향으로 간다"를 보여주는 규칙. 선택지 가중치를 데이터(`choices.tag_weights`)로, 해석을 부품으로 분리한 이유.
- 어휘 트리 매칭은 지금 정확히 같은 태그만 비교. 자식 태그(바다뷰/일출)를 부모(바다뷰)로 올려 부분 점수를 주는 롤업은 다음 단계.
- 파생 테이블을 매 쓰기마다 통째로 재계산. 데이터가 작아서 맞는 선택, 커지면 증분 갱신이나 배치로 전환. 원본이 남아 있으므로 바꿔도 결과는 동일.
- 인증이 없어 `user_id` 를 클라이언트가 전송. 시연 범위.

## 4. AI 활용 및 검토

Claude Code 를 설계 논의 상대와 구현 도구로 사용. 전체 원장은 `AI_LOG.md` 에 작업 순서대로, 프롬프트 원문은
`AI_PROMPTS.md` 에 훅이 자동 기록. 요약:

- **문제 정의는 Owen 이, 검증은 AI 가.** 문제(결제자≠판단자)와 해법 골격(취향 수집 + 공동 후보 보드 + 탈락 데이터 학습)은
  Owen 이 제시. AI 에게는 "이 인과가 실제로 동작하는가"를 따지게 했고, 세 개의 약한 고리(자기보고 취향의 한계, 후보 재정렬만으로는
  탐색 노동이 안 줄어듦, 재결제 레버는 "취향이 앱에 쌓이는 것")를 받아 문제 정의에 반영.
- **AI 의 제안을 버린 것.** 처음 AI 는 취향 테스트를 본체로 하고 공동 후보 보드를 빼자고 제안. Owen 이 설계한 "탈락 숙소의
  특징 + 피드백에서 여행 키워드를 뽑는" 부분이 빠져 있었고, 그것이 더 강한 신호(행동 데이터)라 AI 안을 폐기하고 복원.
  인스타그램 연동 안은 AI 의 반대 근거(API·개인정보·사진 변형)를 받아 이번 범위에서 제외, 발전 방향으로 이동.
- **범위는 마감에서 역산.** AI 가 "작은 결과물" 요구와 남은 시간을 근거로 절단안을 제시, 그 위에서 넣을 것과 뺄 것은 Owen 이 결정.
- **구현은 AI 가, 검증은 실제 실행으로.** 코드는 AI 가 작성. 검토는 코드 읽기가 아니라 브라우저에서 흐름을 끝까지 돌리는
  방식: 멤버 2명 생성 → 여행 생성 → 후보 자동 추천 → 탈락 투표 → 키워드 패널 갱신 → 다음 여행에서 학습 반영.
  이 과정에서 근거 표시가 반대 방향 기여자를 섞어 보여주는 문제를 발견해 수정.
- **인프라는 Owen 이 방향을, AI 가 스키마와 코드를.** 처음 AI 는 "작은 결과물" 을 이유로 DB 없이 내자고 했고 Owen 이 한 번 동의했다가,
  "DB 구조로 생각을 더 잘 전달할 수 있다" 고 판단해 번복. 스택(FastAPI·MySQL)은 Owen 이 쓰는 것으로 결정.
  AI 가 만든 스키마·API 는 브라우저 투표 한 번이 `events` 한 줄 → 파생 테이블 재계산 → 화면 재정렬로 이어지는지를 DB 직접 조회로 확인.
- **스키마는 리뷰로 반이 깎임.** AI 의 첫 스키마는 18개 테이블. Owen 이 (1) 고정 태그 목록이 분화 설계와 모순되고 (2) 규칙 테이블은
  예외 처리 지옥이라고 지적, AI 가 어휘 트리 + 해석기 프로토콜로 재설계해 11개로 축소(이후 좋아요·댓글 테이블이 붙어 13개). 어느 쪽이 냈는지 로그에 기록.
- **AI 가 틀린 것.** 훅 테스트용 JSON 을 잘못 만들어 첫 실행 실패, 공동 후보 보드 설계 누락, MySQL 초기화 SQL 에
  `SET NAMES utf8mb4` 를 빼서 한글 시드가 전부 깨진 채 들어가 FK 실패(API 가 넣는 '커플' 과 시드의 깨진 '커플' 이 불일치).
  스키마를 교과서식으로 과잉 정규화한 것도 AI. 전부 로그에 그대로 기록.

## 5. 실행 방법

```
docker compose up -d --build     # 첫 실행은 MySQL 초기화 때문에 30초쯤 소요
open http://localhost:8080       # 앱
open http://localhost:8080/schema.html   # DB 스키마 (실시간)
open http://localhost:8080/api/docs      # API 문서 (OpenAPI)
docker compose down -v           # DB 볼륨까지 지우고 처음부터
```

- 컨테이너 3개: `staymate-db`(MySQL 8, 호스트 3307) · `staymate-api`(FastAPI, 8000) · `staymate-web`(nginx, 8080).
- 지도("지도에서 고르기")는 Leaflet 과 OpenStreetMap 타일을 인터넷에서 수신. 오프라인 시연이면 지도만 뜨지 않고 나머지는 동작.
- 첫 기동 시 `db/init/*.sql` 이 스키마와 사전 시드(어휘 트리 30·선택지 60·숙소 96)를 넣고, API 가 데모 멤버 10명·여행 6개(과거 4·진행 2)·표·좋아요를 **이벤트로** 생성 (`SEED_DEMO=1`).
- 이벤트와 해석을 나란히 보기: http://localhost:8080/api/events
- DB 직접 보기: `docker compose exec db mysql -uroot -proot staymate --default-character-set=utf8mb4`

시연 순서: 멤버 추가(취향 테스트) 2명 → 새 여행 만들기 → 후보에 유지/탈락 + 이유 → 상단 "이 여행이 추구하는 키워드" 확인 →
"이 멤버로 다음 여행 만들기"에서 이전 학습이 정렬에 반영되는지 확인. 오른쪽 위 "지금 보는 사람"으로 멤버를 바꿔 가며 투표.
